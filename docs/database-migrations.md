# CYVRIX Database Migrations

## Overview

CYVRIX uses Alembic for database schema versioning and migration management.

- **Production schema** is managed by Alembic migrations
- **Test schema** uses `Base.metadata.create_all()` for isolation
- **Development** should use `alembic upgrade head` before starting the application

## Setup

### Local Development

```bash
# Navigate to the API directory
cd apps/api

# Apply all migrations
python -m alembic upgrade head

# Check current migration version
python -m alembic current

# View migration history
python -m alembic history
```

### Creating New Migrations

```bash
# Auto-generate a migration (always review the output!)
python -m alembic revision --autogenerate -m "description of change"

# Create an empty migration (for manual SQL)
python -m alembic revision -m "description of change"
```

**Important:** Always review autogenerated migrations before applying them. Alembic may miss details or suggest unintended changes.

## Common Commands

| Command | Description |
|---------|-------------|
| `alembic current` | Show current migration version |
| `alembic history` | Show all migrations |
| `alembic upgrade head` | Apply all pending migrations |
| `alembic downgrade -1` | Rollback one migration |
| `alembic revision --autogenerate -m "msg"` | Generate migration |
| `alembic heads` | Show head revisions |
| `alembic branches` | Show branch points |

## Production Deployment

### Recommended Order

```bash
# 1. Build new application
docker build -t cyvrix-api .

# 2. Backup database
pg_dump cyvrix > backup_$(date +%Y%m%d_%H%M%S).sql

# 3. Run migrations
python -m alembic upgrade head

# 4. Verify migration
python -m alembic current

# 5. Start application
docker-compose up -d

# 6. Run health check
curl http://localhost:8000/api/health
```

### Migration Safety

- **Backups:** Always backup before production migrations
- **One process:** Only one migration process should run at a time
- **Review:** Never blindly apply autogenerated migrations
- **Downgrade:** Some downgrades may not be safe (documented per migration)

|-------|---------|

| `github_installations` | GitHub App installations |
| `repositories` | Connected repositories |

| `dependencies` | Detected dependencies |
| `findings` | Vulnerability findings |
| `investigations` | AI investigation results |

- `users.email` — UNIQUE
- `users.github_id` — UNIQUE
- `github_installations.installation_id` — UNIQUE
- `repositories.github_repo_id` — UNIQUE
- `repositories(owner, name)` — UNIQUE
- `findings(repository_id, fingerprint)` — UNIQUE
- `investigations.finding_id` — UNIQUE

## Troubleshooting

### "Table already exists" error

This usually means the database was created with `create_all()` outside of Alembic.

**Fix:** Stamp the current revision without running migrations:

```bash
python -m alembic stamp head
```

Then use Alembic for all future schema changes.

### Migration fails on JSONB columns

SQLite (used in tests) doesn't support JSONB. The application uses `JSONBCompat` which falls back to JSON on non-PostgreSQL databases.

### "Password authentication failed"

Check your `DATABASE_URL` environment variable. The application reads from environment, not from `alembic.ini`.

## Technical Notes

- Migrations use async SQLAlchemy for PostgreSQL compatibility
- The `alembic/env.py` imports all application models to ensure accurate autogeneration
- Database credentials are never hard-coded in migration files
- Test databases use SQLite with `create_all()` for isolation
