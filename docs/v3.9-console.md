# V3.9 — Security Workflow Console

**Status:** normative for V3.9 · **Baseline:** V3.8 (`00d0657`) · **Scope:** frontend + one read-only backend endpoint

## 1. Core principle

The backend is the authority; the browser is a client. V3.9 introduces **no
new security authority layer**. It exposes the already-secured V3.1–V3.8
lifecycle to humans: it asks, displays, and requests transitions. The server
authenticates, authorizes, validates, evaluates policy, mutates state, and
returns authoritative state.

The frontend may *display* `approved`, `authorized`, `verified`,
`rollback_allowed`, `policy_decision`, `risk`, `tenant`, `actor`, `digest`,
`role`, and capability. It is never their source of truth.

## 2. Architecture

```
PAGE → COMPONENT → HOOK/QUERY → API CLIENT → ENDPOINT → SERVER AUTHORITY
```

- **Data fetching** lives in `lib/api.ts` (one client) and in the page /
  orchestrator components that own a resource.
- **Presentation** lives in `components/ui/**` (shared primitives) and
  `components/workflow/**` (stage panels). Stage panels receive data and
  callbacks; they do not fetch.
- **Orchestration** lives in `components/workflow/action-lifecycle.tsx`
  (one action's whole lifecycle) and the console pages.

### Shared primitives

`Badge`/`StateBadge`, `Button`, `Card`/`Section`/`PageHeader`/`DataList`/
`DataRow`, `Alert`/`EmptyState`, `CodeBlock`/`JsonBlock`, `ConfirmDialog`,
`Skeleton`/`LoadingBlock`/`ErrorState`, `cn`. One reusable component per
primitive — no `Card2`/`CardNew` variants.

### State presentation

`lib/workflow.ts` maps backend state strings to tones and terminal checks.
Unknown states map to `neutral` and render verbatim — the UI never coerces an
unrecognised state into a success tone and never crashes on one.

## 3. Pages

| Route | Purpose |
|---|---|
| `/actions/[id]` | Approval + full lifecycle hub (timeline, authorization, execution, remediation, verification, rollback) |
| `/executions/[id]` | Bounded execution-run record |
| `/remediations/[id]` | Remediation record + start verification / start rollback |
| `/verifications/[id]` | Server verdict + per-check evidence + regression surfacing |
| `/rollbacks/[id]` | Rollback record + CONFLICT/FAILED safe-stop states |
| `/audit` | Integrity status + chain list (capability-gated) |
| `/audit/[chainId]` | Timeline, event detail, server verification, export, checkpoints |
| `/operations` | Status, state transitions, breakers, reconciliation, repo containment, diagnostics |

Navigation is capability-aware (`components/navigation.tsx`) but hiding a
link is a UX convenience only; the server independently authorizes every
route.

## 4. API contract

All lifecycle clients live in `lib/api.ts`. Request bodies carry **only human
metadata** (`reason`) or are empty; no client function accepts an authority
field, because those fields do not exist in the request schemas
(`extra="forbid"` server-side). Errors expose a machine-readable
`reasonCode` extracted by a strict `[A-Z][A-Z0-9_]{2,63}` pattern — never
free-form server prose.

| Stage | Client functions |
|---|---|
| Authorization | `authorizeAction`, `fetchProposalAuthorizations`, `revokeAuthorization` |
| Execution | `fetchProposalRuns`, `fetchExecutionRun` |
| Remediation | `startRemediation`, `fetchRunRemediations`, `fetchRemediation` |
| Verification | `startVerification`, `fetchRemediationVerifications`, `fetchVerification`, `fetchVerificationChecks` |
| Rollback | `startRollback`, `fetchRemediationRollbacks`, `fetchRollback` |
| Operations | `fetchOpsCapabilities`, `fetchOpsStatus`, `setOpsState`, `fetchRepositoryControl`, `setRepositoryControl`, `fetchBreakers`, `resetBreaker`, `runReconciliation`, `fetchLastReconciliation`, `fetchOpsEvents` |
| Audit | `fetchAuditChains`, `fetchAuditEvents`, `verifyAuditChain`, `fetchAuditCheckpoints`, `fetchAuditIntegrityStatus`, `auditExportPath` |

### Backend addition

`GET /api/ops/capabilities` (authenticated, not capability-gated) returns the
caller's server-derived `role`, `capabilities`, and `step_up_required`. It
grants nothing — every route re-derives the role — and exposes no tenant
data. This is the only backend change in V3.9.

## 5. Security properties

- **No client authority.** No `if (approved) doX()` authority decisions; the
  server rejects unauthorized requests independently of the UI.
- **No fabricated state.** No fake progress, no client verification, no
  hardcoded success. Missing data renders as "—"/"not yet".
- **XSS.** All repository/AI/audit/error text is rendered as React text or
  inert `<pre>`; there is no raw-HTML injection anywhere in the client source
  (enforced by a Jest source-scan test).
- **IDOR.** Every detail page fetches only its own resource; cross-tenant
  access returns 404 server-side and the UI shows a not-found state.
- **CSRF/session.** The existing cookie/session/CSRF model is unchanged; the
  client never stores auth material in `localStorage`/`sessionStorage`.
- **Capability gating.** Operations and audit console controls check the
  server-derived capability set for display only.

## 7. Limitations (documented, not hidden)

- Audit chain verification is **server-computed only**; the browser never
  recomputes digests (by design).
- The console performs bounded polling of non-terminal records (5 s) and
  stops at terminal states; there is no WebSocket/streaming progress, and it
  never invents progress.
- Operations controls are only as useful as the operator bootstrap/role
  provisioning (V3.7 role model unchanged).
- No audit-timeline export UI beyond the deterministic NDJSON download link.
